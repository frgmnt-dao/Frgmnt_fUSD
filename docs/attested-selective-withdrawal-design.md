## 1. Overview

### 1.1 Summary

A new `PoolLogic` entry point, `withdrawCashImmediateWithPlan()`, lets a user redeem fUSD for a specific, non-uniform mix of vault assets, instead of the strict pro-rata slice across every supported asset that `withdrawCashImmediate()` enforces. The user does not choose the mix. A new protocol role, the withdrawal attester, computes it off-chain and signs it, using real-time knowledge of which guards can currently service a withdrawal. The user submits the signed plan in their own transaction. The contract verifies the signature, executes the plan through the existing per-asset guard interface, and independently checks that the total USD value released matches the user's redemption entitlement, whichever assets it came from.

This closes a gap in the current design. Today, if any single guard cannot service its pro-rata slice (an Aave V4 Spoke reserve without enough external liquidity to unwind safely, a Morpho Vault V2 position in a `forceDeallocate` cooldown, a Uniswap V3 position whose TWAP and spot prices currently differ by more than the slippage bound), `withdrawCashImmediate()` reverts for every user, or the manager must set `isImmediateWithdrawEnabled = false` for the entire pool and push everyone onto the three-step queued flow until the problem asset recovers. A plan withdrawal routes around the constrained asset for one request and leaves global withdrawal availability alone.

### 1.2 Problem

`PoolLogic._withdrawCashImmediateToSafe()` computes one `portion = netFusd * 1e18 / totalFundValue()` and applies it to every asset in `getSupportedAssets()` through `_withdrawProcessing(asset, to, portion, complexData)`. These are the names in the validated baseline; the code now lives in `WithdrawalPlanLib` (see [Changes from the validated baseline](#5-changes-from-the-validated-baseline)). This is fair when every asset is equally liquid, but it is all-or-nothing across the asset list. If a portion of any one asset cannot be withdrawn right now, the whole `withdrawCashImmediate()` call reverts, even though the other assets could pay the user. The most realistic case is a complex or flash-loan-unwound position (Aave V3 or V4, Morpho Blue, Morpho Vault V2) whose unwind cannot meet its slippage tolerance because on-chain liquidity for the settlement swap is temporarily thin.

The only existing mitigation is `PoolLogic.setImmediateWithdrawEnabled(false)`, which the manager controls. It is a pool-wide switch that blocks every user's immediate withdrawal, not just those that would touch the impaired asset, and routes everyone through `requestCashWithdraw`, `finalizeCashWithdraw` and `claimCashWithdraw`, which needs manual manager action per request. The known-risk table in `docs/security.md` already records the tension ("a single illiquid asset can still block fund-wide immediate withdrawals, mitigated by the queued withdrawal mode"). This design is a narrower alternative to that mitigation.

### 1.3 Goals

- Let a user redeem fUSD immediately from a subset of the supported assets when one or more guards cannot currently service a uniform pro-rata slice.
- Keep the value-conservation guarantee: a withdrawal can never release more USD value than the fUSD burned entitles the user to, whichever off-chain party composed the mix.
- Reuse the existing `IAssetGuard`, `IComplexAssetGuard` and `ISlippageCheckingGuard` interfaces as they are. No CertiK-validated guard is modified. The orchestration around the guards (`_withdrawProcessing`) is relocated, not left untouched (see [Bytecode size budget](#41-bytecode-size-budget)), but its behaviour toward guards is unchanged.
- Let a plan name the guard the attester validated and, for guards that front several positions (Morpho Blue markets, Aave V4 Spoke reserves), the individual positions to draw from ([Position-level selection](#35-position-level-selection)). New subclass guards that inherit the validated ones provide the selection.
- Bound the damage from a compromised attester key to temporarily unfair asset selection, never fund loss.

### 1.4 Non-goals

- This is not a general user-chosen-allocation withdrawal. The user does not pick which assets they receive; an accountable off-chain role does. See [Trust model](#31-trust-model) for why.
- Not a replacement for `withdrawCashImmediate()` or the queued withdrawal flow, a third, complementary path.
- Not intended to support partial-fill / plan-splitting across multiple transactions in v1 (see [Open questions](#7-open-questions)).
- Position-level selection is offered only while the pool carries no debt in the guard: for Aave V3 any open debt anywhere in the account reverts `SubsetDebtUnsupported` (the reserves then back one shared account, and the validated unwind applies one portion to everything so the health factor is unchanged); for Morpho Blue a selected market with an open borrow reverts the same way (markets are isolated, so debt in an unselected market is fine). Leveraged unwinds stay on the whole-asset path. A guard that cannot select positions at all fails closed (`SubsetNotSupported`).

## 2. How it works

This section explains the whole mechanism in one place, in plain terms, and then shows exactly how it uses the asset guards. Everything here is a description of the code as implemented (`PoolLogic.withdrawCashImmediateWithPlan` and `WithdrawalPlanLib.executeWithdrawalPlan`).

### 2.1 The idea

A normal immediate withdrawal takes the same fraction of every asset the pool holds, so everyone who leaves gets the same mix and nobody gains by leaving first. That breaks down when one asset temporarily cannot pay out its fraction: the withdrawal reverts for everyone. A plan-based withdrawal lets one user redeem for a different mix that avoids the problem asset. An off-chain attester looks at the pool, decides which assets and positions to draw from and how much, and signs that as a plan. The contract does not trust the plan's arithmetic: it re-measures, from the guards' own valuation, how much value actually left the fund, and reverts unless that equals what the user's burned fUSD entitles them to (minus a small, usage-scaled surcharge).

### 2.2 Roles

| Party                                                  | Role                                                                                                                                                                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Attester** (off-chain key, EOA or ERC-1271 contract) | Chooses composition only: which assets, which guard, which positions, how much of each. Signs the plan. Holds no funds and no on-chain permissions.                          |
| **User**                                               | Submits the signed plan in their own transaction. Only the plan's user can execute it. Burns fUSD and receives the assets.                                                   |
| **`PoolLogic`**                                        | The pool. Checks the caller and the feature flag, settles fees/rewards, calls the library, then performs every storage write (nonce, volume accumulator, `accountedAssets`). |
| **`WithdrawalPlanLib`**                                | Delegatecalled library (no storage of its own). Verifies the signature, enforces every bound, dispatches to the guards, measures value.                                      |
| **Asset guards** (validated code)                      | Know how to value and withdraw one kind of asset. They are called exactly as in the pro-rata path and are not told anything about the plan.                                  |
| **`FundCalculationLibrary`** (validated code)          | Computes the pool's value (NAV), the claims and the solvency haircut.                                                                                                        |

### 2.3 Step by step

**Off-chain (attester).** For each supported asset the attester reads which guard serves it, how much of it is liquid now, and for multi-position guards which positions exist (Spoke reserves, Morpho markets, Uniswap NFTs, Aave reserves). It picks the allocations, sets the user's tolerance (`minValueOutBps`, at most 1%) and the ceiling on the surcharge it will accept, and signs the EIP-712 `WithdrawalPlan` for one user, one nonce, one deadline (at most 7 days ahead).

**On-chain.**

```
User ──(plan, signature)──► PoolLogic.withdrawCashImmediateWithPlan
   1. caller must be plan.user; feature must be enabled; settle fees/rewards
   2. WithdrawalPlanLib.executeWithdrawalPlan:
        a. verify signature (attester), deadline, nonce unused, tolerance <= 1%
        b. exit fee + cooldown (same as the normal path) -> netFusd
        c. circuit breaker: add netFusd to the decaying volume; reject if over the cap
        d. burn netFusd from the user
        e. read NAV and claims (uncapped, deficit-adjusted): completeBefore, totalClaims
        f. fairFusd = netFusd, haircut if the pool is underwater
        g. surcharge = fairFusd x (average usage pressure over this withdrawal x max rate); target = fairFusd - surcharge
        h. for each allocation: bind guard, dispatch to the guard, run its transactions,
           forward what the user is owed                      (see 2.4)
        i. fUSD supply must be unchanged; read NAV again: completeAfter
        j. value that left = completeBefore - completeAfter must be within
           [target - tolerance, target + dust]
        k. receipt-side check on the assets actually delivered as tokens
   3. PoolLogic writes: nonce consumed, new volume, accountedAssets reduced by the real outflow
```

The bounds in step j and k are what make the design safe: however the attester composed the plan, the fund cannot lose meaningfully more than `target`, and the user cannot receive meaningfully less (where that can be measured).

### 2.4 How the guards are used

**Which guard serves an asset.** `PoolManagerLogic.getAssetGuard(asset)` looks up the asset's type in `AssetHandler` and then the guard registered for that type in `Governance`. So a guard serves every asset of its type, in every pool, and governance can swap it. That is why each allocation carries the guard the attester validated (`alloc.guard`) and the plan reverts `GuardMismatch` if the current guard differs: a signed plan can never run against replacement code the attester did not review.

**The guard contract.** Every guard exposes `withdrawProcessing(pool, asset, portion, to)`, which returns `(withdrawAsset, withdrawAmount, transactions)`. It is a plan, not an action: a list of calls for the pool to execute. The library runs those calls as the pool (through a delegatecalled context, so `msg.sender` for the target is the pool), then:

- if the guard named a `withdrawAsset`, the library measures the pool's balance change of that token, adds any amount the guard returned itself, and transfers the total to the user (a token leg);
- if the guard returned no `withdrawAsset` (its own transactions already paid the user), nothing more is forwarded (a direct leg).

`portion` is a fraction (1e18 = 100%) of the position's value. In a plan the attester supplies it directly, or supplies a raw `fixedAmount` that the library converts to a portion against the guard's reported balance (capped at 100%).

**Two ways to draw an allocation.**

1. Whole asset (`positionIds` empty): the guard is called exactly as in the normal path and applies the portion to everything it holds for that asset. Every guard supports this, including leveraged Aave V3 and Morpho positions (which unwind through a flash loan).
2. Chosen positions (`positionIds` non-empty): only for guards that fund several independent positions behind one asset and only while there is no debt there. The library calls `withdrawProcessingSubset(pool, asset, portion, to, ids)` on a subclass of the validated guard. The ids must be strictly ascending, at most 32, currently tracked, and the allocation may not also use a fixed amount, complex data or a reserved balance.

**What each guard does in a plan.**

| Guard (asset it serves)                                                              | Whole-asset leg                                                                                                                                    | Position selection                                                                                     |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| ERC20 (a token)                                                                      | Pays `(balance - reserved) x portion` of the token directly. Token leg.                                                                            | Not needed: choose the token as the asset.                                                             |
| Morpho Vault V2, Aave V4 Tokenization (one vault each; one guard serves many vaults) | One `redeem` of the pool's shares (capped by idle or Hub liquidity) to the pool; the underlying is measured by balance change. Token leg.          | Not needed: each vault is its own asset, so a plan draws several vaults with one allocation per vault. |
| Aave V4 Spoke (many reserves)                                                        | Per reserve: `Spoke.withdraw` then transfer to the user, capped by Hub liquidity (a shared ledger stops two reserves double-claiming). Direct leg. | By `reserveId`.                                                                                        |
| Morpho Blue (many markets)                                                           | No debt: withdraw supply shares and collateral straight to the user. With debt: flash-loan unwind.                                                 | By market id, only while no tracked market has debt.                                                   |
| Uniswap V3 (many NFTs)                                                               | Per NFT: `decreaseLiquidity` with TWAP-priced minimums, then `collect` to the user. Direct leg.                                                    | By `tokenId` (the subclass keeps only the selected NFTs of the validated plan).                        |
| Aave V3 (many reserves, one shared account)                                          | No debt: `Pool.withdraw` then transfer, per reserve. With debt: flash-loan unwind that keeps the health factor.                                    | By reserve token address, only while the account has no debt at all.                                   |

The four subclass guards inherit the validated guards unchanged and add one function (plus a capability marker); the validated sources are not edited. Where a subset guard sizes a liquidity ceiling, it uses the minimum over the selected positions, so an illiquid position the plan did not pick cannot throttle one it did.

**The guards' arithmetic is not the security boundary.** The library never relies on a guard having sized its legs correctly. It reads the pool's value through the validated valuation (`computeImmediateWithdrawPortion`, which reads each guard's balance, net-realizable value and deficit) before and after the allocations run. Whatever the guards did, the value that left must land in the band. A buggy or over-generous guard, or a plan that picks the wrong positions, simply reverts.

### 2.5 Worked example

A pool holds $1,000,000: $600,000 in an ERC20 (USDC) and $400,000 in an Aave V4 Spoke, where reserve 2 (WETH, $200,000) is nearly frozen. A user redeems 10,000 fUSD (no exit fee, solvent pool, surcharge 0).

- A normal withdrawal would need 1% of every asset, including reserve 2, and would revert.
- The attester signs a plan: USDC allocation with fixed amount 5,000 USDC, and the Spoke allocation for reserve 1 only (WBTC, liquid) at a portion worth $5,000.
- On-chain: the guard for USDC returns the token amount (a token leg); the Spoke subclass returns a `withdraw` and a `transfer` for reserve 1 only (a direct leg). Reserve 2 is never touched.
- NAV before $1,000,000, after $990,000: value out = $10,000 = target, inside the band. The receipt-side check sees the 5,000 USDC delivered as a token, well within bounds. The plan succeeds.

If the attester had also included reserve 2, the frozen reserve would deliver less than requested, the value out would fall below the band, and the whole transaction would revert atomically.

### 2.6 Failure cases and the checks that catch them

| Risk                                                     | Caught by                                                                                                   |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Plan tampered after signing, wrong user, replay, expired | EIP-712 signature over the whole plan, user binding, single-use nonce, deadline                             |
| Guard swapped by governance after signing                | Guard binding (`GuardMismatch`)                                                                             |
| Plan takes more than the entitlement                     | Upper bound on NAV outflow, and the receipt-side upper bound                                                |
| User paid less than the entitlement                      | Lower bound on NAV outflow (tolerance capped at 1%), and the receipt-side lower bound when no leg is direct |
| Compromised attester drains through many valid plans     | Pool-wide decaying volume cap; manager/`factoryOwner` kill switch; 24h delayed rotation                     |
| Mid-plan deposit or mint through a callback              | fUSD supply must be unchanged across the allocations                                                        |
| Plan starves a queued withdrawal                         | A plan cannot draw an asset with Pending queued requests                                                    |
| Selecting positions with debt                            | Subset guards refuse selection while debt exists                                                            |
| Anything unexpected in a guard's plan                    | The subset filters are fail-closed; any failed call reverts the whole transaction                           |

## 3. Design

### 3.1 Trust model

The attester, not the user, chooses the asset mix.

A design in which the user picks and self-signs their own mix (following the pattern of `TokenLogic.depositWithAuthorization`) invites adverse selection. Each rational user would redeem the healthiest and most liquid assets first and leave the impaired or illiquid ones to whoever exits later, which moves loss from early leavers to remaining holders. Here a dedicated withdrawal attester signs the plan instead. It is an automated backend service operated by the protocol, and it can see which guards are constrained right now (Aave V4 Spoke reserve utilisation, Morpho Vault V2 `forceDeallocate` state, Uniswap V3 spot and TWAP deviation). A user cannot push a bad asset onto the remaining holders.

Key management differs from every other role in the codebase. The `manager`, the `factoryOwner` and the Timelock proposers are cold keys, likely multisigs. The attester is a hot key in a process that signs continuously, so server compromise, key leakage and supply-chain compromise of the signing service are the main threats, and [Limits on a compromised attester key](#38-limits-on-a-compromised-attester-key) is written around them.

The attester's power is bounded on-chain. Its signature decides which assets a withdrawal draws from and in what proportion. The contract measures the value that actually leaves the fund and reverts unless it matches the user's entitlement within a small tolerance, in either direction ([Value conservation](#36-value-conservation)). A fully compromised key can therefore choose the composition of a withdrawal that a user starts, which brings back the adverse-selection problem for as long as the compromise lasts. It cannot make the fund pay out more than that withdrawal's entitlement, and it cannot create withdrawals for users who do not submit them.

### 3.2 Execution flow

The diagram in [2.3](#23-step-by-step) shows the sequence. This section lists the same steps with the checks each one applies and the errors they raise. The attester service ([Plan composition](#37-plan-composition)) has already read the pool, chosen the assets and amounts, and signed the plan.

When the user submits it, `PoolLogic.withdrawCashImmediateWithPlan` does the following:

1. **Entry checks in `PoolLogic`.** The caller must be `plan.user` (`NotPlanUser`), the feature must be enabled (`ImmediateWithdrawalDisabled`), and the user's fees and rewards are settled with the same checkpoint every other entry point uses.
2. **`WithdrawalPlanLib.executeWithdrawalPlan`**, called by `delegatecall`:
    1. Read the pool state it needs through the pool's public getters.
    2. Verify the attester's signature, that the deadline has not passed and is at most 7 days ahead (`PlanDeadlineExpired`, `PlanDeadlineTooFar`), that the nonce is unused (`PlanNonceAlreadyUsed`), that `minValueOutBps` is at most 100 (`MinValueOutBpsTooHigh`), and that `fusdAmount` is nonzero (`ZeroAmount`).
    3. Apply the exit fee and cooldown exactly as `withdrawCashImmediate` does, giving `netFusd`. The manager pays neither.
    4. Add `netFusd` to the decaying volume accumulator and reject if it exceeds the cap (`AttestedWithdrawVolumeCapExceeded`). This happens before anything is burned.
    5. Burn `netFusd` from the user.
    6. Read the fund value and the outstanding claims, and compute `fairFusd`, which equals `netFusd` unless the pool is underwater. Revert if `fairFusd` is zero or `netFusd` is below 1e16 (`WithdrawAmountTooSmall`).
    7. Compute the surcharge from the recent volume, reject it if it exceeds the plan's signed ceiling (`SurchargeTooHigh`), and set `target = fairFusd - surcharge`.
    8. For each allocation: check the asset is supported and not repeated, bind the guard, refuse assets with queued requests, resolve the portion, dispatch to the guard, run its transactions and forward what the user is owed.
    9. Require that fUSD's total supply is unchanged since the burn (`FusdSupplyChanged`), read the fund value again, and require the value that left to lie within `[target - tolerance, target + dust]` (`ValueConservationViolated`).
    10. Check the value of what was delivered as tokens against the same band (the receipt-side check, see [Value conservation](#36-value-conservation)).
    11. Emit `CashWithdrawImmediateProRata` and `AttestedWithdrawPlanExecuted`.
3. **Writes in `PoolLogic`.** Mark the nonce consumed, store the new volume state, and reduce `accountedAssets` by the value that actually left.

The nonce is written after the library returns because the library holds no storage. That is safe: `nonReentrant` blocks re-entry during the call and any revert undoes every change, so a plan cannot execute twice.

### 3.3 Data structures and signing

```solidity
struct AssetAllocation {
    address asset; // must be a supported asset of the pool
    address guard; // the guard the attester validated; must equal getAssetGuard(asset)
    bytes32[] positionIds; // optional: draw only these positions; empty means the whole asset
    bool useFixedAmount; // true: draw `fixedAmount` raw units, false: draw `portion`
    uint256 portion; // 1e18 = 100%; must not exceed 1e18 (InvalidPortion)
    uint256 fixedAmount; // raw asset units, used when useFixedAmount
}

struct WithdrawalPlan {
    address user; // the only address that may execute the plan
    uint256 fusdAmount; // gross fUSD redeemed, before the exit fee
    uint256 minValueOutBps; // accepted shortfall below target, at most 100 (1%)
    AssetAllocation[] allocations; // sparse: omitted assets are never touched
    uint256 nonce; // single use per user
    uint256 deadline; // unix seconds, at most 7 days ahead
    uint256 maxAcceptableSurchargeBps; // the attester's ceiling on the surcharge; 0 rejects any
}
```

`allocations` is sparse, so excluded assets cost no guard call. `ComplexAsset[] complexAssetsData` stays an unsigned call parameter, matched to allocations by asset address, so the user keeps the same control over swap slippage as in `withdrawCashImmediateSafe`.

**EIP-712.** The typed-data hashes are:

```
AssetAllocation(address asset,address guard,bytes32[] positionIds,bool useFixedAmount,uint256 portion,uint256 fixedAmount)
WithdrawalPlan(address user,uint256 fusdAmount,uint256 minValueOutBps,AssetAllocation[] allocations,uint256 nonce,uint256 deadline,uint256 maxAcceptableSurchargeBps)
```

The domain is `name = "Frgmnt PoolLogic"`, `version = "1"`, plus `chainId` and the pool's address, so a signature is bound to one pool on one chain. `PoolLogic` does not inherit `EIP712Upgradeable`: inheriting it would add bytecode and cached storage to a contract with almost no room. Instead `WithdrawalPlanLib._hashPlan` computes the same domain separator inline. Under `delegatecall`, `address(this)` is the pool, so the digest is identical to the one the OpenZeppelin base contract would give.

**Signature check.** The attester may be an EOA or an ERC-1271 contract, for example a co-signing multisig. `WithdrawalPlanLib._isValidSignatureNow` tries ECDSA recovery first and falls back to an `isValidSignature` static call when the attester address has code. It is hand-written because OpenZeppelin's `SignatureChecker` (5.4.0) pulls in the `mcopy` opcode, which this repository's Paris target does not support. For a Safe attester, note that the digest passed to `isValidSignature` is the raw EIP-712 digest, which the Safe wraps in its own typed data, so its owners must sign the wrapped hash.

### 3.4 Entry point

```solidity
function withdrawCashImmediateWithPlan(
    WithdrawalPlan calldata plan,
    bytes calldata attesterSignature,
    ComplexAsset[] calldata complexAssetsData
) external nonReentrant returns (address[] memory outAssets, uint256[] memory outAmounts);
```

The caller check uses plain `msg.sender`, not `_actionSender()`. `_actionSender()` trusts any address on the manager-controlled `allowedCallbackSenders` list to name an arbitrary acting user, with no consent bound to the transaction. Routing this function through it would let a manager force a withdrawal against a user's balance. Until that mechanism has a real consent binding, this function keys off `msg.sender` only, like `withdrawCashImmediateSafe` and `withdrawCashImmediateToSafe`.

The function is independent of `isImmediateWithdrawEnabled`. Its purpose is to give relief in exactly the situation where a manager would otherwise switch immediate withdrawals off for everyone, so tying the two flags together would defeat it. The manager keeps an emergency stop by disabling both.

Per-allocation rules, in the order the library applies them:

- The asset must be supported and appear once (`AssetNotSupported`, `DuplicateAllocation`).
- The guard must equal the pool's current guard for the asset (`InvalidGuard` if none, `GuardMismatch` if different).
- The asset must have no queued withdrawal requests waiting on it (`AssetHasPendingWithdrawRequests`).
- With `positionIds` set, the position-level rules in [Position-level selection](#35-position-level-selection) apply.
- Otherwise, with `useFixedAmount`, the guard's balance must be nonzero (`ZeroAssetBalance`) and `portion = min(fixedAmount * 1e18 / balance, 1e18)`. Without it, `portion` is used directly and must not exceed 1e18 (`InvalidPortion`).
- The withdrawal then runs through `WithdrawalPlanLib.withdrawProcessing`, the same per-asset dispatch the pro-rata path uses, including its slippage checks and reserved-balance handling.

`CashWithdrawImmediateProRata` is reused for the outputs so that a second, near-identical dynamic-array event does not have to be compiled in. A plan withdrawal is not a pro-rata one, so indexers must treat a `CashWithdrawImmediateProRata` that is emitted with an `AttestedWithdrawPlanExecuted` in the same transaction as attester-composed. Legs paid directly by a guard's own transactions (Spoke, Morpho, Uniswap V3 and Aave V3 subset legs) are absent from `outAssets` and `outAmounts`, as they are on the whole-asset path.

### 3.5 Position-level selection

A supported asset is `{address asset, bool isDeposit}` and its behavior is defined by the guard registered for it (`getAssetGuard(asset)`, set globally per asset type by governance). Several kinds of guard exist (the table below has one row per kind), and a plan has to be able to address all of them:

| Guard kind                                                            | What `asset` is                  | Positions behind it                     |
| --------------------------------------------------------------------- | -------------------------------- | --------------------------------------- |
| One position per asset (ERC20, Morpho Vault V2, Aave V4 Tokenization) | the token / vault / tokenization | exactly one, nothing to select          |
| Pseudo-asset fronting many positions (Morpho Blue, Aave V4 Spoke)     | the Morpho singleton / the Spoke | markets (`Id`) / reserves (`reserveId`) |
| Uniswap V3 position manager (no debt)                                 | the NFT manager                  | LP NFTs (`tokenId`)                     |
| Aave V3 pool (selectable only with no debt)                           | the pool                         | reserves (underlying token address)     |

So each `AssetAllocation` names, and the attester signs: the asset, the guard, the positions inside the guard, and the amount (the surcharge is a plan-level field).

**Guard binding (all allocations).** `alloc.guard` must equal the pool's current `getAssetGuard(asset)` (`GuardMismatch`), and the guard must be non-zero. Guards are governed per asset type and can be swapped; without the binding, a plan the attester signed against reviewed guard code would silently execute against a replacement.

**Position selection (`positionIds` non-empty).** Only the listed positions are drawn, each at `portion` of its own value. Rules, all enforced on-chain:

- the guard must implement `ISubPositionGuard` (`isSubPositionGuard()` + `withdrawProcessingSubset()`); otherwise `SubsetNotSupported`, a plan is never silently widened to the whole asset;
- ids strictly ascending (`PositionIdsNotAscending`: also rules out duplicates), at most 32 per allocation (`TooManyPositionIds`);
- not combined with `useFixedAmount`, complex-asset data, or a reserved balance on the asset (`InvalidSubsetAllocation`);
- `portion <= 1e18` (`InvalidPortion`);
- the guard itself rejects any id that is not currently tracked for the pool.

**Where the selection logic lives: validated guards are not edited.** Four new contracts inherit the validated guards and only add the subset entry point, reusing the validated `internal` helpers:

- `AaveV4SpokeSelectiveAssetGuard is AaveV4SpokeAssetGuard`: iterates the selected reserveIds instead of every tracked reserve, through the base contract's own per-reserve routine, so Hub-liquidity capping and the shared liquidity ledger apply unchanged; the ledger now only counts selected reserves, so an illiquid reserve the plan did not pick can no longer starve one it did.
- `MorphoBlueLendingPoolSelectiveAssetGuard is MorphoBlueLendingPoolAssetGuard`: reuses the base collectors and no-debt transaction builder, filters their output to the selected market ids, and sizes the liquidity ceiling as the minimum across the selected markets only (the base guard uses the minimum across all tracked markets, so one near-fully-utilised market throttles everything). v1 scope: a selected market with an open borrow position reverts `SubsetDebtUnsupported`; leveraged unwinds stay on the pro-rata path. Morpho markets are isolated, so drawing from a debt-free market cannot affect the health of a different, levered one, which is simply left untouched.
- `AaveV3LendingPoolSelectiveAssetGuard is AaveV3LendingPoolAssetGuard`: selectable only while the pool has no Aave V3 debt at all (`SubsetDebtUnsupported` otherwise: with debt every reserve backs one account whose health factor the validated guard preserves by scaling collateral and debt together). It calls the validated `_withdrawCollateralAndTransfer` for the full set of reserves and keeps only the `Pool.withdraw` / token `transfer` pairs of the selected reserves, and sizes the liquidity ceiling over the selected reserves only (the validated `_maxSafePortion` is the minimum across all reserves, so one near-fully-utilised reserve throttles every other). Position id = the reserve's underlying token address; ids must be supported assets of the pool that are Aave reserves. Aave's own health-factor check on `withdraw` is an additional hard backstop. The filter is fail-closed (`UnexpectedTransaction`). Limit: the plan is built over every supported asset before filtering.
- `UniswapV3SelectiveAssetGuard is UniswapV3AssetGuard`: reimplements nothing. It calls the validated `withdrawProcessing()` for the full plan (every owned NFT, with its TWAP-priced slippage minimums and fee-only collect caps) and keeps only the `decreaseLiquidity`/`collect` transactions whose `tokenId` (first argument word) is a selected NFT. The filter is fail-closed: any other transaction, or one not targeting the position manager, reverts `UnexpectedTransaction`. Ids are NFT tokenIds, must be currently owned by the pool and strictly ascending. LP positions carry no debt, so withdrawing some NFTs cannot affect any other position. Limit: the validated function prices every owned NFT before the filter runs, so an unselected NFT whose pricing reverts still reverts the call, and gas grows with the number of owned NFTs.

Deploying any subclass means governance re-pointing the asset type's guard (`setAssetGuard`; the guard is resolved per asset TYPE through `Governance.assetGuards`, so the swap applies to every asset of that type in every pool). The Morpho and Aave V3 guards carry owner-set configuration (Morpho: `uniV3Fee`, `defaultSlippageBps`, buffers, `requiresApproveReset`; Aave V3: the same plus the exact-in/exact-out Uniswap paths, and a constructor-seeded USDT `requiresApproveReset` entry) and the Uniswap V3 guard carries admin-set configuration (`withdrawalSlippageBps`, `withdrawalTwapWindow`, per-pool `minimumPoolLiquidity`) that the new instance starts without and must be re-seeded to match before the swap; the deploy script does this and verifies it.

**Selection rule: debt-free means selectable.** The single-position guards (ERC20, Morpho Vault V2, Aave V4 Tokenization) are selected at the asset level: each vault or token is its own supported asset, so a plan chooses among them with one allocation per asset. The multi-position guards are selected at the position level, and every one of them is selectable exactly while the pool has no debt there: Aave V4 Spoke (supply-only), Uniswap V3 (LP NFTs carry no debt), Morpho Blue markets without a borrow, and the Aave V3 pool while it has no debt anywhere in the account. What is not selectable is a debt-bearing position: an Aave V3 account with any debt, or a Morpho Blue market with an open borrow; those use the whole-asset path, whose unwind is designed for leverage.

**Why the value bound is what makes this safe.** The guards' own arithmetic is not the security boundary, the plan's two-sided bound is, and it is measured on the uncapped complete NAV (see [Value conservation](#36-value-conservation)). A subset guard that sized a leg wrongly, or a plan that picked positions summing to more or less than the entitlement, fails `ValueConservationViolated` and reverts atomically.

### 3.6 Value conservation

The pro-rata path bounds a withdrawal only from above: it reverts if more than `netFusd + 1e15` leaves the fund. Under-delivery is not a realistic failure there, because every asset is taken at the same portion and the sum tracks `netFusd`. For an attester-composed plan it is a real failure mode: the chosen assets may not hold enough at execution time because of price drift or a race with another withdrawal, and a user would burn fUSD and receive less value than it entitles them to. The plan path therefore enforces a band, and reverts the whole transaction, burn included, when either side is violated.

With `target = fairFusd - surcharge`, and `valueDelta` the fall in the fund's value over the allocations loop:

```
target - target * minValueOutBps / 10_000  <=  valueDelta  <=  target + DUST_TOLERANCE
```

- **Upper bound.** `DUST_TOLERANCE` is the fixed constant 1e15, as in the pro-rata path. The attester has no influence over how much the fund may overpay, so it stays a constant.
- **Lower bound.** `minValueOutBps` is chosen by the attester and capped at `MAX_MIN_VALUE_OUT_BPS` (100, 1%), so a compromised attester cannot widen it enough to let meaningful value leak from a user. In calm markets it can be small; when prices or balances may drift between signing and execution it can be widened slightly to avoid spurious reverts.
- An empty `allocations` array fails the lower bound with no special case, because `valueDelta` is 0 and `target` is positive.

**The bound uses `fairFusd`, not `netFusd`.** The pro-rata path sizes its portion against a solvency-haircut share (`FundCalculationLibrary.applyClaimsHaircut`) whenever outstanding claims exceed the fund's value. If the plan path paid at par while every other withdrawal took the haircut, an underwater pool would let early leavers extract more than their share, which is the problem the claims haircut exists to prevent. The library derives `fairFusd` from the outputs of `computeImmediateWithdrawPortion` through the validated `applyClaimsHaircut`, leaving both validated functions unchanged. In a solvent pool `fairFusd` equals `netFusd`.

**Value is measured on the uncapped NAV.** `computeImmediateWithdrawPortion(pool, netFusd, 1)` returns `completeFundValue`, the oracle-priced, reserved-excluding, deficit-adjusted fund value with no liquidity cap (the `1` only avoids its zero early-return). It is read before the loop and again after it. The liquidity-capped value the pro-rata path uses is unsuitable here. For a guard whose ceiling is the minimum across several positions (Morpho Blue markets, Aave V3 reserves) the capped value does not move linearly when only some positions are drawn. That could make legitimate plans revert and, worse, weaken the upper bound by the inverse of the binding liquidity ratio. The uncapped figure also feeds `computeAccountedAssetsReduction`, which expects it. A temporary liquidity gap therefore shows up as a lower-bound failure after the loop, not as an early revert.

**Receipt-side check.** The NAV bounds measure value leaving the fund, which is not always what the user receives. `completeFundValue` floors at zero, so a pool with a deficit could let the last claimant draw more real assets than the floored NAV drop records. And value lost inside a guard's own transactions (swap slippage, a flash-loan premium on a leveraged unwind) leaves the NAV without reaching the user. So the library also values what was delivered as tokens (`assetValue` over `outAssets` and `outAmounts`). That value may never exceed `target + DUST_TOLERANCE`, and when no leg was paid directly by a guard's own transactions it may not fall short of the lower bound by more than `DUST_TOLERANCE`. Value paid directly by guards cannot be measured here. Those guards have no swap leg and refuse debt, so no deficit is involved; the residual is described in [Security analysis](#312-security-analysis).

### 3.7 Plan composition

The value bound is a band: `[target - target * minValueOutBps / 10_000, target + DUST_TOLERANCE]`. The upper edge is fixed and has no tolerance, so the only room a plan has above its aim is whatever the attester leaves below `target`. Between the attester signing and the transaction executing, the value a plan draws can move: a deposit or a donation raises an asset's balance, another user's pro-rata withdrawal lowers it, an oracle tick reprices it. What each kind of leg does when that happens:

| Leg kind                           | Balance rises by `D`                                                         | Balance falls                                         |
| ---------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------- |
| Whole-asset, **fixed amount**      | Draw stays `fixedAmount` (converted to `fixedAmount / balance` at execution) | Draw stays `fixedAmount`, capped at the whole balance |
| Whole-asset, **portion**           | Draw grows by `portion x D`; reverts once it passes the upper edge           | Draw shrinks; reverts once it passes the lower edge   |
| Position-level (portion, required) | Draw follows the positions' value (interest, price); same band applies       | Same                                                  |

So a portion plan aimed exactly at `target` reverts on a donation of `dust / portion`, and any third party can cause that at almost no cost. That is a liveness problem (the user retries with a fresh signature), never a value one: the upper bound is what stops the over-draw. The rules that remove it are off-chain and are implemented, with tests, in `scripts/utils/withdrawalPlanBuilder.ts`, a pure-arithmetic module the attester service imports:

1. **Whole-asset legs use fixed amounts** (`composeFixedAmountAllocations`). Balance rises then cannot move the draw.
2. **Aim at the middle of the band**, `target - slack / 2` (`aimValue`), never at `target`, and sign a real band (`minValueOutBps` of 1 to 100). To push such a plan over the upper edge a griefer must lift the draw by about half the band, which costs them `slack / (2 x portion)` of their own money, donated to the fund, instead of dust. `driftRoom` reports the room in each direction for a chosen aim.
3. **Quote the surcharge with the contract's own arithmetic** (`quoteSurcharge`, verified against the contract's event value in `test/AttestedWithdrawal.test.ts`) so `target` and the signed `maxAcceptableSurchargeBps` are exact rather than estimated.
4. **Short deadlines, and a `staticCall` against the latest state immediately before releasing the signature.**

Position-level legs must be portions (the contract rejects a fixed amount there), so rule 1 does not apply to them; rule 2 does, and the position's value drift (interest, a price tick) is small next to the half-band. The module is guidance in executable form: the contract does not, and cannot, force an attester to follow it, because loosening the upper edge to make careless plans safe would weaken the bound that protects the fund from a compromised attester.

#### Reference attester service

`services/attester/` is a reference implementation of the attester that applies these rules end to end (see its `README.md`). It reads a consistent snapshot of the pool at one block, composes whole-asset fixed-amount legs pro rata by what each allowed asset can pay now, quotes the surcharge with the contract's arithmetic, signs, and releases the signature only after a simulation of the plan from the requesting user against the same state passes. It refuses (with a machine-readable code) when the feature is disabled or stopped, when it is not the pool's current attester, inside the user's exit cooldown, when liquidity or the volume cap would not allow the plan, or when it has already signed more than a configured amount that has not yet executed or expired. It supports whole-asset legs of plain guards only; position-level plans and assets needing `complexAssetsData` are out of its scope. The private key sits behind a two-method `PlanSigner` interface so a KMS or HSM can hold it; the bundled wallet signer is for development. It is tested against a real `PoolLogic` (`test/AttesterService.test.ts`): plans it signs are executed on-chain, and each refusal, the HTTP layer and the service's copies of the contract's arithmetic are checked. A test of it found and fixed one real defect: the library adds `netFusd` to the claims because the pool burns first, so a read taken before the burn must subtract it, or an underwater pool's plans are wrongly reduced.

### 3.8 Limits on a compromised attester key

The value bound limits what one plan can do. It does not limit how many plans a compromised key can sign before someone notices. The realistic worst case for an always-on backend signer is many small, individually plausible plans, signed over hours or days, that collectively steer a disproportionate share of the healthy assets to an attacker and leave the impaired ones concentrated for the remaining holders. Three controls address it.

**Instant revoke, delayed appoint.** Switching the feature off is instant and needs no coordination. Appointing a new attester takes at least 24 hours. See [Roles and storage](#39-roles-and-storage).

**A decaying volume cap (circuit breaker).** The pool tracks the cumulative value released through `withdrawCashImmediateWithPlan`, separately from `withdrawCashImmediate`. A plan that would push the tracked total over `maxAttestedWithdrawVolumePerWindow` reverts, and the user falls back to the ordinary or queued path. This needs no detection of the compromise; it caps the loss from an undetected one, like a per-day withdrawal limit at an exchange.

A fixed window that resets to zero every N hours lets an attacker release a full cap just before the boundary and another just after it, up to twice the intended cap. So the accumulator decays continuously, with the same shape as `SlippageAccumulator`:

```
elapsed = now - lastWithdrawTimestamp
decayed = elapsed < window ? accumulated * (window - elapsed) / window : 0
newTotal = decayed + netFusd            // revert if newTotal > cap
```

Details enforced in `WithdrawalPlanLib._checkAndRecordVolume`:

- The setter enforces a window of at least one hour (`MIN_ATTESTED_WITHDRAW_DECAY_WINDOW`). A window of 0 would make `elapsed < window` never true, so the accumulator would forget everything between transactions. The library also refuses to run with a window of 0, in case the setter was never called.
- A window above 30 days is treated as 30 days at the point of use, so an enormous stored value cannot overflow the arithmetic and disable the feature.
- The stored total is a `uint128`, so a new total above `type(uint128).max` reverts instead of truncating.
- The accumulator meters `netFusd`, the amount burned.

The cap is pool-wide, not per user. A per-user cap would not stop one compromised key signing many different users' individually legitimate withdrawals. The cost is that one large withdrawal, or a burst, can use up the window for everyone else, who then use the ordinary or queued path. The manager can raise the cap if legitimate demand keeps hitting it. It should start conservative, for example a small multiple of typical daily volume, and a cap that is hit often under normal conditions is a signal to raise it on purpose. `SlippageAccumulator` and this accumulator are two independent copies of the same formula.

**The breaker is not independent of the manager.** The manager sets the cap and the window and controls attester proposals. A manager colluding with an attester can therefore release roughly `cap * (1 + T / window)` in time `T`. The breaker bounds a compromised attester key. The independent control against a compromised manager is the `factoryOwner`'s latched stop. Making the cap `factoryOwner`-settable or raising the window floor would tighten this and is a product decision.

Together these limit a compromised key to misallocating composition, never magnitude, for a capped, monitored and quickly revocable volume of withdrawals.

### 3.9 Roles and storage

| Item                                                         | Written by                                                                 | Notes                                                                                     |
| ------------------------------------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `withdrawalAttester`                                         | `activateWithdrawalAttester` (anyone, after the delay) and the initializer | The active signer.                                                                        |
| `pendingWithdrawalAttester`, `pendingAttesterActivationTime` | `proposeWithdrawalAttester` (manager)                                      | Cleared when the feature is switched off.                                                 |
| `attesterRotationDelay`                                      | `setAttesterRotationDelay` (`factoryOwner` only), initializer              | At least `MIN_ATTESTER_ROTATION_DELAY` (24 hours). Not manager-settable.                  |
| `consumedPlanNonce[user][nonce]`                             | `withdrawCashImmediateWithPlan`                                            |                                                                                           |
| `isAttestedWithdrawEnabled`                                  | `setAttestedWithdrawEnabled` (manager or `factoryOwner`)                   | Independent of `isImmediateWithdrawEnabled`. Starts false.                                |
| `attestedWithdrawOwnerStopped`                               | `setAttestedWithdrawEnabled` (`factoryOwner` only)                         | The latched stop. While set the manager cannot enable the feature or propose an attester. |
| `attestedWithdrawVolume`                                     | `withdrawCashImmediateWithPlan`                                            | The decaying accumulator (`uint64` timestamp, `uint128` value).                           |
| `maxAttestedWithdrawVolumePerWindow`                         | `setMaxAttestedWithdrawVolumePerWindow` (manager)                          | 0 blocks all plan withdrawals, which is safe.                                             |
| `attestedWithdrawDecayWindow`                                | `setAttestedWithdrawDecayWindow` (manager)                                 | At least one hour.                                                                        |
| `maxSurchargeBps`                                            | `setMaxSurchargeBps` (`factoryOwner` only)                                 | Clamped to 100 in the library; 0 disables the surcharge. See [Surcharge](#310-surcharge). |

The eleven variables are appended after the last baseline variable (`pendingCashWithdrawCount`), in slots 23 to 33 in the order above. `PoolLogic` has no `__gap`, so append-only placement is what protects the layout of the live proxy.

Rotation is deliberately asymmetric, the way the fee logic already is (`setFeeNumerator` lowers a fee at once, `announceFeeIncrease` and `commitFeeIncrease` raise one after a delay):

- **`setAttestedWithdrawEnabled(false)` is instant** and can be called by the manager or the `factoryOwner`. It removes a capability, so there is no reason to delay it, and it must be available immediately when the backend key is suspected. It also clears any pending attester proposal, so a malicious proposal still inside its delay cannot be activated later.
- **The `factoryOwner`'s call latches the stop.** The manager otherwise controls the rotation and the volume cap, so a compromised or colluding manager could appoint its own attester and lift the breaker with nobody able to stop it. Without a latch the stop could be defeated by re-enabling at once, or by proposing an attester, waiting out the delay while disabled, and enabling again. With the latch, re-enabling needs the `factoryOwner` to lift the stop first, after reviewing the attester, and then the manager to enable. The `factoryOwner` calling `setAttestedWithdrawEnabled(true)` only lifts the latch and never enables the feature itself. A manager-initiated disable is not latched. On mainnet the `factoryOwner` is a Safe, so the stop needs a Safe quorum, while the manager's own disable remains the no-coordination lever. If the manager address is ever set equal to the `factoryOwner` while a stop is latched, that address acts as the manager and cannot lift it until the manager changes.
- **`proposeWithdrawalAttester(candidate)`** is manager-only. It sets `pendingAttesterActivationTime = now + attesterRotationDelay`, and reverts while the stop is latched (`AttestedWithdrawOwnerStopActive`) and while `attesterRotationDelay` is still 0 (`AttestedWithdrawalNotInitialized`). The second check matters because the delay defaults to zero before the initializer runs, which would let a manager propose and activate an attester in consecutive blocks and bypass the 24 hour floor.
- **`activateWithdrawalAttester()`** can be called by anyone once the delay has passed.

`attesterRotationDelay` is settable only by the `factoryOwner`. The delay exists to give monitoring time against a manager who is compromised or colluding, and a manager who could also shorten it could propose a malicious attester and zero the delay in one step. This follows `PoolManagerLogic._performanceFeeNumeratorChangeDelay`, which is set through the `onlyFactoryOwner` `setFactoryConfig`. The decay window has a floor for a similar reason, explained in [Limits on a compromised attester key](#38-limits-on-a-compromised-attester-key). `maxSurchargeBps` is `factoryOwner`-only because the manager does not collect the surcharge, so the risk is a manager quietly setting it to zero to make the feature look free.

Replacing trust in a key is therefore slow and observable, and outside the sole control of the actor being guarded against, while withdrawing trust from a suspect key is instant. The events `WithdrawalAttesterProposed`, `WithdrawalAttesterActivated`, `AttestedWithdrawEnabledSet`, `AttesterRotationDelaySet`, `MaxAttestedWithdrawVolumePerWindowSet`, `AttestedWithdrawDecayWindowSet` and `MaxSurchargeBpsSet` should feed monitoring. An unexpected `WithdrawalAttesterProposed` is the most valuable alert, because after its delay it can reintroduce cherry-picking with no further code change.

### 3.10 Surcharge

#### Problem

The normal pro-rata withdrawal has a property people rely on without noticing: equal treatment. Everyone who leaves gets the same slice of every asset, so it does not matter who leaves first. A plan-based withdrawal gives up that property: it lets a user leave with the assets that are easiest to exit and leaves the harder ones behind. That is exactly what the feature is for (route around the asset that is stuck), but it has a price: each such withdrawal shifts the pool's remaining mix toward the assets nobody wanted, and it hands an advantage to whoever uses the path first. If nothing prices that, the path is a free option, and heavy use of it looks like a slow run: the early users take the good assets at par and the late ones are left with what is stuck.

#### Mechanism

The value bound guarantees that a withdrawal takes no more, and delivers no less, than its entitlement. It does not price a different cost that plan withdrawals put on everyone who stays. A plan can skip whichever assets are impaired, so each one moves the fund's remaining composition further toward the assets nobody wanted to touch. The pro-rata path has no such cost, because it takes every asset in the same proportion. A manager can rebalance afterwards, but that trade costs real money (fees and price impact, often against the thin assets that caused the skew), so the cost only moves to the fund. Funds that face redemption pressure use swing pricing or a dilution levy: a redemption that pushes the fund away from its target allocation pays an amount that stays in the fund. The surcharge does the same.

It is computed in `WithdrawalPlanLib.executeWithdrawalPlan` once `completeBefore` and the updated volume state are known, and before the allocations loop, so a plan above the attester's signed ceiling fails cheaply with `SurchargeTooHigh`:

```
volumeBefore = decayed accumulated volume before this withdrawal
volumeAfter  = volumeBefore + this withdrawal's netFusd
base         = completeBefore + volumeBefore        // the fund as it stood before the recent volume left
pressure     = ( min(volumeBefore * 1e18 / base, 1e18) + min(volumeAfter * 1e18 / base, 1e18) ) / 2
effectiveMax = min(maxSurchargeBps, MAX_SURCHARGE_BPS_CEILING)
surchargeBpsX18 = pressure * effectiveMax           // bps scaled by 1e18, not truncated
revert SurchargeTooHigh if ceil(surchargeBpsX18 / 1e18) > plan.maxAcceptableSurchargeBps

surchargeAmount = fairFusd * surchargeBpsX18 / (1e18 * 10_000)
target          = fairFusd - surchargeAmount
```

- **Average pressure, constant base.** The charge is the area under a linear price curve. Each dollar leaving pays the pressure it faces at that point, meaning recent volume as a share of the fund before that volume left, and the withdrawal pays the average over the dollars it takes. Two earlier shapes made the total depend on how a withdrawal was cut. Charging every dollar at the end-of-withdrawal pressure over-charged one large plan against the same amount split into several (a five-way split saved about 16%), and measuring against the current, already shrunk fund made later chunks pay more than a single plan. With the constant base above, the charges of consecutive chunks telescope. For cumulative volumes `A_0 < A_1 < ... < A_n` the total is `sum(x_i * (A_(i-1) + A_i) / (2 * base)) = (A_n^2 - A_0^2) / (2 * base)`, the same as one plan of the same size. This holds up to decay between plans, deposits and rounding, and a test compares one 500-of-1,000 plan with five 100 plans.
- **Pressure comes from the circuit breaker's accumulator**, expressed as a fraction of the fund's own value, so it needs no new state and captures a single large withdrawal and a burst of small ones alike. A composition-aware charge would price the skew more precisely but needs the plan compared with live per-asset weights, which is more logic and more reads than `PoolLogic`'s size budget can take. The proxy does not distinguish a withdrawal that drains one thin asset from an equal one spread over many healthy assets. This is an accepted imprecision.
- **Both sides of the value bound use `target`.** The lower bound only tolerates `minValueOutBps` below its reference, and that tolerance does not account for a surcharge the attester could not know when choosing it. Reducing what is delivered without moving the bound it is checked against would make a correct surcharged withdrawal revert.
- **The attester signs its own ceiling.** Pressure depends on live state (another plan can land first and move the shared accumulator), so `maxAcceptableSurchargeBps` lets the attester bound its exposure to that drift, the same trust pattern as `minValueOutBps`, with a separate hard-coded ceiling enforced by the protocol.
- **The withheld value stays in the fund through the ordinary accounting.** The user burns their full entitlement of fUSD and receives `target`, so the real outflow is smaller than a surcharge-free withdrawal's by exactly the surcharge. `accountedAssets` is reduced by that real outflow, which keeps it equal to NAV: no overhang that would swallow the next real yield, and no gap that the next accrual would read as yield and charge the performance fee on. `surchargeAmount` is informational and is emitted in `AttestedWithdrawPlanExecuted`.
- **What the retained slice is.** fUSD redeems at par while the pool is solvent, so extra collateral does not raise anyone's redemption value, and it is not recognised as yield either. It raises the pool's collateralisation, a buffer against a solvency haircut if losses occur and against the cost of restoring the pool's composition. It is a price on the skew, not a payout to stakers. Paying it to stakers as yield would be a different design that interacts with the performance fee, and it was not chosen.
- **Continuous ramp.** There is no threshold to cross. A mechanism that switches on at a line gives anyone watching the state a reason to race ahead of it, which would work against the users the feature is meant to help.
- **Governance.** `maxSurchargeBps` is settable only by the `factoryOwner` and starts at 0. The library clamps the applied rate at 1% whatever is stored, so the setter needs no bound check of its own, which saves bytecode. A hard-coded ceiling cannot stop a zero, and setting it to zero disables the surcharge, which is why the manager is kept away from the setter.

#### Worked figures

Pool value $1,000,000, no recent volume, `maxSurchargeBps` = 100 (the 1% ceiling):

| Single withdrawal | Share of pool | Average rate | Surcharge |
| ----------------- | ------------- | ------------ | --------- |
| $10,000           | 1%            | 0.005%       | $0.50     |
| $100,000          | 10%           | 0.05%        | $50       |
| $500,000          | 50%           | 0.25%        | $1,250    |
| $1,000,000        | 100%          | 0.50%        | $5,000    |

The rate at the end of the withdrawal is twice the average (for the $100,000 exit it rises from 0% to 0.10%), and the average is what is charged. The same $100,000 taken as five $20,000 plans inside one window pays $2 + $6 + $10 + $14 + $18 = $50, exactly the same as one plan, because each plan is charged only for the stretch of the curve it covers. So the charge is quadratic in size, small for ordinary use and meaningful only for a large or rapid exit, and cutting a withdrawal up neither saves nor costs anything.

#### Who pays and who benefits

- **The withdrawing user pays**, from their own entitlement, and has agreed to it in advance through the attester-signed ceiling.
- **The value stays in the pool as extra collateral.** The user burns fUSD worth `fairFusd` but takes out only `target`, so the pool holds more than the remaining claims require. It is not paid out to anyone and not recognised as yield (a yield event would also trigger the performance fee); the bookkeeping is arranged so `accountedAssets` keeps tracking the pool's value.
- **Who benefits:** fUSD is redeemed at par while the pool is solvent, so extra collateral does not raise any redemption value. What it does is raise the pool's collateralization: a buffer that protects every remaining holder's principal against a solvency haircut if losses occur, and that can absorb the cost of restoring the pool's composition (trades, slippage). It protects the peg; it does not add yield.

#### Alternatives considered

| Alternative                                                     | Why it was not chosen                                                                                                                                                                                      |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No surcharge                                                    | Leaves the first-mover advantage unpriced; the path becomes a free option and a run route.                                                                                                                 |
| A flat fee                                                      | Charges the same for a tiny withdrawal and a pool-draining one; does not scale with the harm and cannot deter concentrated use.                                                                            |
| A composition-aware charge (price the actual skew of each plan) | More precise, but needs the plan compared against live per-asset weights: extra logic and reads that `PoolLogic`'s bytecode budget could not absorb. Usage pressure is a cheaper proxy for the same thing. |
| Pay the surcharge out to stakers as yield                       | Would interact with the performance fee (the manager would collect on it) and change the reward accounting; not needed to protect principal.                                                               |
| A threshold that switches the charge on                         | Creates a cliff people can race; a continuous ramp has none.                                                                                                                                               |

The design borrows a standard tool from funds with redemption pressure: swing pricing or a dilution levy, where redemptions that would push the fund away from its target allocation pay an amount kept inside the fund.

#### Model selection

**Requirements the model had to meet.** These were fixed before choosing a formula:

| #   | Requirement                                                                     | Why                                                                                                     |
| --- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| R1  | The charge grows with the harm done to remaining holders.                       | A price unrelated to the harm neither compensates nor deters.                                           |
| R2  | Ordinary, small use is almost free.                                             | The feature exists so users can route around a stuck asset; taxing that would defeat its purpose.       |
| R3  | No cliff or threshold.                                                          | A threshold is a line people can race to stay under.                                                    |
| R4  | Bounded worst case, enforced in code.                                           | Whatever governance or a bug does, a user can never lose more than a known fraction.                    |
| R5  | No new state and negligible bytecode.                                           | `PoolLogic` has almost no size headroom; a model needing per-asset weights or new storage does not fit. |
| R6  | The attester can bound its own exposure to drift between signing and execution. | The rate depends on live state the attester cannot know exactly when signing.                           |
| R7  | Compatible with the existing accounting.                                        | It must not create phantom yield, an overhang, or a performance-fee event.                              |

**Why a rate that grows with cumulative usage (R1, R2).** Take a pool of value `N` whose liquid assets are a share `l` of it. A plan that draws only liquid assets amount `V` leaves the remaining holders with two costs:

1. a carrying cost: they hold `(1 - l) * V` more illiquid dollars than under a pro-rata exit, and each illiquid dollar costs something to hold or eventually exit, which is linear in `V`;
2. a liquidity-exhaustion risk: the remaining pool's liquid share `(l*N - V) / (N - V)` falls as cumulative `V` grows, reaching zero when `V = l*N`, so the risk of being unable to meet the next withdrawal grows faster than linearly in cumulative volume.

For a single small withdrawal the second cost is negligible and the first is small, so the right charge is close to zero (R2). As cumulative volume rises the second cost dominates and the charge per dollar must rise with it (R1). A marginal rate proportional to cumulative pressure (`V_cumulative / N`) has exactly this shape: near zero at small volume, rising continuously, and so total charge quadratic in size. It is the simplest function with that property (R5). Charging the average of that marginal rate over the withdrawal, rather than its end value, is what makes the total independent of how the withdrawal is cut into plans.

**Why the accumulator decays.** The skew is not permanent: the stuck asset recovers, the manager rebalances, other users withdraw. Volume from long ago should therefore weigh less than volume from the last hour. The circuit breaker already maintains a continuously decaying volume accumulator, so the surcharge reuses it: one state variable, one decay window, consistent behaviour, no fixed window to game (R3, R5).

**Why the denominator is the pool's own value.** Dividing by the same uncapped, deficit-adjusted NAV that the value bound uses makes the rate scale-free: taking 10% of a pool costs the same rate whatever the pool's size, and the surcharge is measured against the same figure the bound is checked against.

**Why it applies to `fairFusd`, not `netFusd`.** In an underwater pool the user's real entitlement is the haircut amount. Charging on the nominal amount would charge on value the pool cannot pay out.

**Why the ceiling is hardcoded at 1% (R4).** The governed maximum is a plain storage value that a setter writes without a bound check (to save bytecode). The library therefore clamps the applied rate at 1% at the point of use, so a compromised owner or a typo cannot exceed it. The marginal rate reaches the maximum only at 100% pressure, and the charged rate is the average over the withdrawal, so the worst case (the entire pool exiting at once) costs the user 0.5% of their entitlement, and ordinary sizes cost a small fraction of that.

**Why the attester signs a ceiling (R6).** Another plan can land between signing and execution and raise the pressure. The signed ceiling lets the attester refuse a rate it did not expect, using the same trust pattern as `minValueOutBps`: the attester proposes its own tolerance and the protocol enforces a separate hardcoded limit.

**Why the value is retained, not distributed (R7).** The user burns `fairFusd` worth of fUSD but takes `target`, so the real outflow is smaller by exactly the surcharge. `accountedAssets` is reduced by the real outflow, which keeps it equal to the pool's value: no overhang that would swallow the next real yield, and no gap that the next accrual would read as yield and charge performance fee on. An early version subtracted the surcharge from the reduction as well; that double-counted it, was caught in review, and is covered by a test that asserts the invariant.

**Sensitivity.** The maximum scales every figure linearly. Charge on a $100,000 withdrawal from a $1,000,000 pool (pressure 0 to 10%, average 5%, no prior volume) and on a $500,000 withdrawal (0 to 50%, average 25%):

| `maxSurchargeBps` (max rate at 100% pressure) | $100,000 exit | $500,000 exit |
| --------------------------------------------- | ------------- | ------------- |
| 0 (default, off)                              | $0            | $0            |
| 25 (0.25%)                                    | $12.50        | $312.50       |
| 50 (0.50%)                                    | $25           | $625          |
| 100 (1.00%, the code ceiling)                 | $50           | $1,250        |

**Evidence, and what is not evidence.** The shape is justified by the requirements above and by the two-part cost argument; the arithmetic is exact and is pinned by tests (the surcharge amount for a known pressure, the ceiling boundary, the clamp, zero default, the exact event value, no double count in an underwater pool). A randomized run of mixed pro-rata, plan, staking and queued operations kept `accountedAssets` equal to the pool's value after every step and recognised no spurious yield or fee. What is not evidence: nothing here is calibrated against real usage or a measured cost of holding the illiquid assets. The 1% ceiling and the choice of a linear ramp are judgment. That is why the default is 0 and why the doc recommends observing real plan usage before enabling a small maximum.

#### Limitations

- **It measures usage, not skew.** A plan that draws a pro-rata-like mix still pays; a small but very skewed plan pays little. This is an accepted imprecision, chosen for cost.
- **It is small by design.** The ceiling is 1% and the typical charge is a fraction of a percent. It prices the externality and deters heavy use; it does not make the skew harmless, and it is not a substitute for the volume cap, the kill switch or manager rebalancing.
- **It is split-invariant only up to decay, deposits and rounding.** Cutting a withdrawal into plans costs the same in total (see the numbers above). Time between plans lets the accumulator decay, so a very slow drip pays a little less, which is the intended behaviour of a decaying measure, and a deposit between plans lowers the pressure the same way for one plan or several.
- **It is a price, not a guarantee.** It builds a buffer that is a fraction of the value moved; it cannot promise the remaining holders are made whole.

#### Governance and calibration

`maxSurchargeBps` is set by the `factoryOwner` (not the manager, who does not receive the money and could otherwise be tempted to zero it to make the feature look free), starts at 0, and cannot exceed the hardcoded 1% ceiling whatever it is set to. The attester's per-plan ceiling bounds drift between signing and execution. A sensible rollout is to launch with 0, observe real usage and the attester's compositions, and only then enable a small maximum. Because the rate is a fraction of the maximum, the effective cost for ordinary sizes stays far below it.

### 3.11 Interaction with existing systems

- **Guards.** Every validated `IAssetGuard`, `IComplexAssetGuard` and `ISlippageCheckingGuard` implementation works unchanged for whole-asset allocations. Position-level selection comes from four new subclass guards (see [Position-level selection](#35-position-level-selection)), not from edits to the validated ones. The orchestration around the guards was relocated into `WithdrawalPlanLib` and is shared by the pro-rata and plan paths ([Bytecode size budget](#41-bytecode-size-budget)).
- **Reserved balances.** Whole-asset legs go through the same per-asset dispatch as the pro-rata path, which subtracts `reservedAssetBalance` before sizing. A position-level allocation on an asset with a reserved balance is refused (`InvalidSubsetAllocation`). A plan may not draw an asset that has Pending queued requests (`AssetHasPendingWithdrawRequests`, read from `pendingCashWithdrawCount`), so it cannot starve `finalizeCashWithdraw` for that asset.
- **Cooldown and exit fee.** Identical to `withdrawCashImmediate`. The feature changes which assets a withdrawal draws from, not whether it is allowed.
- **`accountedAssets`.** Reduced by the value that actually left the fund, plus the loss share `computeAccountedAssetsReduction` adds under FNA-42. The surcharge needs no adjustment. It is the difference between `fairFusd` and what the user receives, and it stays in the fund through the smaller NAV drop. Subtracting it again would leave `accountedAssets` above NAV and swallow the next real yield.

### 3.12 Security analysis

**Identity and consent.** The function keys off plain `msg.sender` (see [Entry point](#34-entry-point)). The signature covers the user, so a plan cannot be executed by anyone else.

**Replay and staleness.** A single-use nonce per user and a deadline of at most 7 days prevent replay and stop a signature being held as a free option or surviving an off and on toggle of the feature. An attester should sign a deadline of minutes, which also limits drift between signing and execution. If an asset is removed from the supported list after signing, the on-chain support check rejects it.

**Guard swaps.** Each allocation carries the guard the attester validated, and the plan reverts if the pool's current guard differs, so a signed plan cannot run against replacement guard code the attester never reviewed.

**Front-running.** A pending plan gives an observer no edge: it commits to amounts and a value bound and either executes within them or reverts.

**Gas.** The `allocations` array is bounded by the supported-asset list, which is capped at `_maximumSupportedAssetCount` (50 by default), and position lists by 32 ids per allocation.

**Dust.** The upper bound allows at most 1e15 wei (0.001 USD) of over-payment per call, and each call needs an attester signature and a fresh nonce. `MIN_PLAN_NET_FUSD` (1e16, one cent net) makes the burn at least ten times that amount, so the extractable dust is at most about 10% of the volume the breaker meters. This bounds what a compromised key can do; it does not make the trade unprofitable, and on a low-fee chain a compromised attester could repeat it, limited by the volume cap. Smaller redemptions use the pro-rata path.

**Mid-plan minting.** A deposit made from a token or guard callback while the loop runs would be netted out of the value bound (the refunded deposit offsets the withdrawal) and still mint fUSD. The library therefore requires the fUSD supply to be unchanged across the loop (`FusdSupplyChanged`). No hook-bearing asset is supported today, so this is defence in depth. It lives in the library so that the validated deposit hooks in `PoolLogic` stay identical to the baseline.

**Debt gates on position selection.** The Aave V3 subset guard uses Aave's own account-wide debt view, which covers a reserve that is no longer a supported asset and stable-rate debt. The Morpho subset guard requires that no tracked market carries debt, because the validated NAV deducts a modelled unwind cost across every leg once any market has debt, which a debt-free in-kind exit does not incur. A selected debt-free market next to a levered one would otherwise leave about 0.75% more value than NAV records at default settings.

**Initializer ordering.** `initializeAttestedWithdrawal` reverts `AutoCompoundingNotInitialized` while the auto-compounding index is still zero. Running the version-3 initializer first would consume version 3 and make `initializeAutoCompounding` revert forever, breaking stake, unstake and harvest.

#### Accepted residual risks

None of these breaks fund safety. Each is stated so a reviewer can disagree with it.

- **Deficit reading fails open (inherited).** `_guardDeficit` in the validated shared code fails open if a deficit-reporting guard's `getDeficit` succeeds before the loop and fails after it, which would understate `valueDelta` by the deficit. The pro-rata path behaves the same way, and it cannot be forced under EIP-150 gas rules. It was left unchanged because the function is validated code.
- **Floor at zero with a deficit (mitigated).** `completeFundValue` floors at zero, so with a deficit the last or only claimant could draw more real assets than the NAV drop records. The receipt-side upper bound closes this for every leg whose value is measurable. It cannot see value guards deliver directly, but those guards refuse debt, so no deficit is involved.
- **Lower bound measures the pool side (mitigated).** `valueDelta` includes value lost inside a guard's own transactions, which the user never receives. When no leg is paid directly by a guard, the receipt-side lower bound makes a leveraged unwind that loses value in swaps revert instead of shortchanging the user. Where a leg is paid directly (Spoke, Morpho, Uniswap V3, Aave V3 subset) the value cannot be measured here. Those paths have no swap leg, and Uniswap V3 has TWAP minimums, so the exposure is limited to the guards' own slippage configuration.
- **Guard return values.** The library transfers whatever `(withdrawAsset, withdrawAmount)` a guard returns. A governed guard already controls arbitrary calls executed as the pool through its returned transactions, which is strictly stronger, so an allow-list would add nothing. The four subset guards return `(address(0), 0, txs)`.
- **Incomplete NAV.** An unpriced or unvaluable position anywhere makes the NAV incomplete and reverts a plan, even one that selects unrelated assets (`IncompleteNAV`). This is a liveness limit in the safe direction.
- **Morpho subset reads.** A Morpho subset call still reads every tracked market through the validated collectors, so an unselected market whose IRM or oracle reverts can revert the call, and gas grows with the number of tracked markets. Only the liquidity throttle is decoupled from unselected markets. Donating supply shares to a nearly fully utilised selected market can throttle its ceiling toward zero, which is the base guard's accepted residual; the attester can drop that market from the plan.
- **Queue mode.** Plans are independent of `isImmediateWithdrawEnabled`, so in queue mode they are the only immediate exit. A plan cannot draw an asset with Pending queued requests, so it cannot starve finalization for that asset. Requests already Pending on the live pool before the upgrade have a zero counter and are not protected, which is why the upgrade scripts refuse to run while any is Pending.
- **Portion-based plans are fragile if composed carelessly (mitigated off-chain).** The upper bound is `target + dust` with no band, so a portion plan aimed exactly at `target` reverts on any rise in that asset's balance between signing and execution, and a third party can cause that with a dust-sized donation. The contract cannot loosen the edge without weakening the drain bound, so the fix is in composition ([Plan composition](#37-plan-composition)). What remains is that the contract accepts a careless plan if the attester signs one, and that position-level legs must be portions. This is a liveness exposure, not a value one.
- **The surcharge is a price, not a guarantee.** It is quadratic in size and charged on the average pressure over each withdrawal, so cutting a withdrawal into several plans costs the same in total, up to decay, deposits and rounding. At the governed maximum of 1%, a full-pool exit pays 0.5% of the entitlement. The 1% ceiling stays hard-coded in the library, and the recommendation to observe real plan usage before enabling a small maximum is unchanged.
- **Stale or lagging valuation.** NAV before and after is read through guard view functions. A guard whose view under-accrues interest compared with what the withdrawal realises (an Aave V4 Spoke share index, a Vault V2 share price) would let a plan pull that accrued difference on top of `target`, and an attester could pick the asset whose oracle lags the market. Both are bounded by the oracle deviation, the volume cap and the 1% band. Morpho Blue and Aave V3 aTokens accrue in their views. The Spoke, Tokenization and Vault V2 accrual behaviour is validated baseline code that has not been re-verified for this path.
- **Custody of governance roles.** Older scripts recorded `GOVERNANCE_SAFE` as a single-key EOA, and the team has since confirmed the deployed contracts are controlled by the multisig. The latched stop, `setMaxSurchargeBps` and the rotation-delay floor are only as independent as the `factoryOwner`, so they rest on that multisig. Both upgrade scripts read the owners on-chain at run time and refuse to build a batch on a mismatch.

## 4. Implementation

### 4.1 Bytecode size budget

`PoolLogic` is compiled with `viaIR` and `optimizer.runs = 1`, so the usual size levers were already spent. At the baseline its deployed size was 24,447 of 24,576 bytes, a headroom of 129 bytes. The new entry point, its governance functions, events, errors and storage are far larger than that, so code had to move out of `PoolLogic` first. It is now 24,426 bytes with 150 bytes of headroom. Because there is so little room left, any further change to `PoolLogic` needs a size check first (`npm run check:contract-size`).

**A linked library.** `PoolTxExecutor` and `FundCalculationLibrary` already show the pattern: a library with `external` functions is deployed as its own contract and reached by `delegatecall`, so its bytecode does not count against `PoolLogic`'s limit. `WithdrawalPlanLib` follows it. An internal function such as the old `_withdrawProcessing` cannot be called from a delegatecalled library, because it exists only as jumps inside `PoolLogic`. The per-asset dispatch was therefore moved into the library, and both the pro-rata loop and the plan loop call that one copy. This avoids shipping two implementations of the same logic that could drift apart.

**What moved.** The library holds `withdrawProcessing` (the per-asset dispatch), `executeProRataWithdrawal` and `executeWithdrawalPlan`. Between them they take over the fee and cooldown computation, the fee transfer, the burn and the value math for both paths, plus signature verification, plan validation, the circuit breaker and the surcharge. `PoolLogic` keeps only the storage writes those results feed (`accountedAssets`, `consumedPlanNonce`, `attestedWithdrawVolume`). The relocation freed roughly 3,400 bytes, and the feature's own additions to `PoolLogic` then used nearly all of it. Later additions were paid for by moving code into the library:

- The library reads the pool state it needs (attester, fUSD address, volume state, `maxSurchargeBps`, nonce status) through the pool's public getters, at the very start of the call and before any external interaction, instead of `PoolLogic` building and passing a ten-field struct. This saved about 394 bytes at the cost of a few thousand gas per plan withdrawal.
- `CashWithdrawImmediateProRata` and `AttestedWithdrawPlanExecuted` are emitted from inside the library. A `delegatecall` preserves the emitting address for `LOG` as it does for `SSTORE`, so the logs are indistinguishable from ones `PoolLogic` emitted. `PoolLogic` still declares both events, so its ABI stays complete for indexers.

**No storage in the library.** A `delegatecall`ed library runs against the caller's storage, so a state variable declared in the library would occupy the caller's slots by position. That is the bug class behind the 2017 Parity multisig freeze. `WithdrawalPlanLib` declares no storage. Every function takes what it needs as parameters and returns results, and `PoolLogic` performs every `SSTORE`. Reentrancy is unaffected: `nonReentrant` on the outer entry point still covers the call, because a `delegatecall` runs in the same frame and storage context and is not a new external boundary.

**Two copies to keep in sync.** `WithdrawalPlanLib._chargeWithdrawFee` deliberately duplicates the exit-fee formula in `PoolLogic._applyWithdrawFeeFusd`, which stays for `FundCalculationLibrary`'s other call sites. `MAX_MIN_VALUE_OUT_BPS` is declared in both `PoolLogic` (public) and the library (private), because a library cannot read a constant from the contract that calls it. Nothing checks either pair automatically, so a change to one must be made in both.

**Allocation loop structure.** The per-allocation work is split into `_processAllocation`, `_validateAllocation` and `_drawAllocation`, with the running state in one memory struct. A single function holding every local of the loop exceeds the stack limit under the coverage instrumentation, which had broken `npm run coverage`. Behaviour is unchanged.

If more room is ever needed, the remaining levers are converting any remaining `require` strings in `PoolLogic` to custom errors and confirming `metadata.bytecodeHash` is not inflating the size.

### 4.2 Upgrade and storage migration

The migration follows the pattern of `initializeAutoCompounding` (`reinitializer(2)`):

```solidity
function initializeAttestedWithdrawal(
    address attester_,
    uint256 attesterRotationDelay_,
    uint256 attestedWithdrawDecayWindow_,
    uint256 maxAttestedWithdrawVolumePerWindow_,
    uint256 maxSurchargeBps_
) external onlyOwner reinitializer(3) {
    if (withdrawalAttester != address(0)) revert AttestedWithdrawalAlreadyInitialized();
    if (compoundedRewardIndex == 0) revert AutoCompoundingNotInitialized();
    if (attester_ == address(0)) revert ZeroAddress();
    if (attesterRotationDelay_ < MIN_ATTESTER_ROTATION_DELAY) revert RotationDelayTooShort();
    if (attestedWithdrawDecayWindow_ < MIN_ATTESTED_WITHDRAW_DECAY_WINDOW)
        revert DecayWindowTooShort();

    withdrawalAttester = attester_;
    attesterRotationDelay = attesterRotationDelay_;
    attestedWithdrawDecayWindow = attestedWithdrawDecayWindow_;
    maxAttestedWithdrawVolumePerWindow = maxAttestedWithdrawVolumePerWindow_;
    maxSurchargeBps = maxSurchargeBps_;
}
```

- **Floors apply from the start.** Both minimums are enforced in the initializer as well as in the setters, so the feature cannot launch in an already-defeated state. `maxSurchargeBps_` has no floor, so a pool can launch with the surcharge off and enable it later. The check on `withdrawalAttester` is redundant, because `reinitializer(3)` reverts a second call first, and is kept as a second guard.
- **The feature starts disabled.** The initializer leaves `isAttestedWithdrawEnabled` false, because the path pays out user funds on the strength of a hot key. The manager enables it after the attester service and its parameters have been verified.
- **Separate owner transaction.** The initializer must run as its own owner-sent transaction after an empty-data `upgradeAndCall`, because inside `upgradeAndCall` the sender is the ProxyAdmin, not the owner. On a pool that has not yet run `initializeAutoCompounding` it must run strictly after that call. `docs/upgradeable-contracts-notes.md` has the full sequence and the reason the order is fixed.
- **Storage.** The eleven new variables are appended after `pendingCashWithdrawCount`, never inserted, and `maxSurchargeBps` was placed last for that reason even though it is related to the volume variables. The relocation into the library declares no storage and does not affect the layout. The migration ships in the same Timelock upgrade batch as the implementation swap.

### 5.3 PoolLogic.sol

`git diff 4922f72 HEAD -- contracts/contracts/PoolLogic.sol` is large (348 lines added, 320 removed) because most of it is code relocation, not new logic. The change has three parts.

**1. Code moved out of `PoolLogic` into `WithdrawalPlanLib` (pure relocation).** These internal functions and structs no longer exist in `PoolLogic`; their bodies live in the new library, called through `delegatecall`:

| Removed from `PoolLogic`                                       | Now in `WithdrawalPlanLib`                                                  |
| -------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `_withdrawProcessing` (per-asset guard dispatch)               | `withdrawProcessing` (public, shared by both withdrawal paths)              |
| `_withdrawOne`, `_withdrawProRataInternal`, `_withdrawProRata` | `executeProRataWithdrawal` (the same loop, fee/cooldown/burn ordering kept) |
| `_checkCallResult`                                             | `_checkCallResult`                                                          |
| `_withdrawableFundValue` (one-line wrapper)                    | direct calls to `FundCalculationLibrary.computeWithdrawableFundValue`       |
| structs `WithdrawOutputs`, `WithdrawProcessingLocalVars`       | library-local equivalents                                                   |

The public entry points `withdrawCashImmediate`, `withdrawCashImmediateTo`, `withdrawCashImmediateSafe` and `withdrawCashImmediateToSafe` keep their signatures, modifiers and access rules. `_withdrawCashImmediateToSafe` now checks the enabled flag and the zero amount, calls `WithdrawalPlanLib.executeProRataWithdrawal`, and then performs the same `accountedAssets` reduction (`computeAccountedAssetsReduction`, FNA-42) and emits the same two events as before. The order of operations inside the moved code is unchanged: enabled check, zero-amount check, manager bypass or cooldown, exit fee, fee transfer, burn, fund value, portion, per-asset processing and transfer, the upper value bound, then the accounting.

**2. New feature code added to `PoolLogic`.**

- Storage, appended after the last baseline variable (`pendingCashWithdrawCount`), never inserted: `withdrawalAttester`, `pendingWithdrawalAttester`, `pendingAttesterActivationTime`, `attesterRotationDelay`, `consumedPlanNonce`, `isAttestedWithdrawEnabled`, `attestedWithdrawVolume`, `attestedWithdrawDecayWindow`, `maxAttestedWithdrawVolumePerWindow`, `maxSurchargeBps`, `attestedWithdrawOwnerStopped` (slots 23–33; baseline slots 0–22 are unchanged in slot, offset and type).
- `withdrawCashImmediateWithPlan` (the new entry point) and its governance functions: `proposeWithdrawalAttester`, `activateWithdrawalAttester`, `setAttestedWithdrawEnabled`, `setAttesterRotationDelay`, `setMaxAttestedWithdrawVolumePerWindow`, `setAttestedWithdrawDecayWindow`, `setMaxSurchargeBps`, and the migration initializer `initializeAttestedWithdrawal` (`reinitializer(3)`, mirroring the existing `initializeAutoCompounding` pattern).
- Events and errors for the above.

**3. Errors that moved to `IPoolLogic`.** Errors thrown from both `PoolLogic` and the library (for example `SlippageExceeded`, `InvalidFundValue`, `AssetNotSupported`) are now declared on `IPoolLogic` so the library can use them. Selectors are unchanged and every error still appears in `PoolLogic`'s ABI.

**ABI compatibility.** Comparing the compiled ABI of `PoolLogic` at the baseline and at this branch: no function, event or error was removed or changed; the difference is additions only (the new functions, events and errors above). Existing integrations and decoders keep working.

**Bytecode size.** `PoolLogic` deployed size went from 24,447 to 24,426 bytes (EIP-170 limit 24,576), i.e. headroom from 129 to 150 bytes, after adding the feature.

### 5.4 Why the changes were needed

**The size limit forced the relocation.** At the baseline, `PoolLogic` had only 129 bytes of EIP-170 headroom. The new entry point, its governance functions, its events and errors and its storage are far larger than 129 bytes (the relocation freed roughly 3,400 bytes, and the feature's own additions to `PoolLogic` then used nearly all of it: the net change in deployed size is only −21 bytes, from 24,447 to 24,426), so it cannot be added to `PoolLogic` without first freeing bytecode. The only structural options are to move existing code out of `PoolLogic`, or not to add the feature.

**Why the code moved into a library rather than being copied.** The per-asset guard-dispatch logic (`_withdrawProcessing`) is needed by both the existing pro-rata path and the new plan path. Copying it into a second location would have duplicated roughly 3,400 bytes of validated logic and created two copies that must be kept in sync. Instead it was moved once and both paths call the single copy. This is also the smaller review surface: the moved code is byte-for-byte the same logic, and the new path reuses it rather than reimplementing it.

**Why a library, and why `delegatecall`.** `PoolLogic` already links `FundCalculationLibrary` and `PoolTxExecutor` externally; `WithdrawalPlanLib` follows the same established pattern. Under `delegatecall` the library runs in `PoolLogic`'s own context, so `address(this)`, `msg.sender` semantics (`burnFrom` is called by the pool) and storage reads behave exactly as before. The library declares no storage of its own and never writes `PoolLogic`'s state: every `SSTORE` (nonce, volume accumulator, `accountedAssets`) is performed by `PoolLogic` itself after the library returns, which avoids the library-storage bug class behind the 2017 Parity multisig freeze.

**Why the EIP-712 domain and signature check are hand-rolled.** Inheriting `EIP712Upgradeable` would add bytecode and cached storage to `PoolLogic`. The library computes the same domain separator inline (`address(this)` resolves to the pool under `delegatecall`), and verifies the signature with `ECDSA` plus a manual ERC-1271 `staticcall`, because OpenZeppelin's `SignatureChecker` (5.4.0) pulls in the `mcopy` opcode, which this repository's Paris target does not support.

**Why position-level selection uses new subclass guards.** A plan must be able to name the guard and the individual positions behind guards that front many positions (Morpho Blue markets, Aave V4 Spoke reserves, Uniswap V3 NFTs). Adding that to the validated guards would have meant editing CertiK-validated code. Instead `AaveV4SpokeSelectiveAssetGuard`, `MorphoBlueLendingPoolSelectiveAssetGuard`, `UniswapV3SelectiveAssetGuard` and `AaveV3LendingPoolSelectiveAssetGuard` inherit the validated guards without overriding any of their functions and add a capability marker (`isSubPositionGuard`) and one function, `withdrawProcessingSubset`, that reuses the validated code (internal helpers for Spoke and Morpho; for Uniswap the validated `withdrawProcessing` output, filtered). The validated sources stay untouched and the new review surface is four small files. Governance opts in per asset type by re-pointing the guard (see the upgrade notes); until then the validated guards run as before.

**Why the two interface changes.** `IPoolLogic` gained the plan structs, the shared errors and the getters the library reads through self-calls. `IPoolManagerLogic` gained `factoryOwner()` (already implemented by the unchanged `PoolManagerLogic`) so `PoolLogic` can give the `factoryOwner` an independent emergency stop and gate the rotation delay, the same role that already gates the performance-fee delay.

### 5.5 Checking the relocated code

The relocated code is meant to be behavior-identical. That claim has been checked in three separate ways during internal review, and reviewers can repeat each:

1. **Line-by-line comparison** of the removed `PoolLogic` functions against `WithdrawalPlanLib.withdrawProcessing`, `executeProRataWithdrawal` and `_checkCallResult`: same checks, same order, same error selectors, same slippage baseline, same balance-delta handling and `externalProcessed` semantics. The one intentional difference is that `reservedAssetBalance(asset)` is read through a self-call instead of a direct mapping read (a mapping cannot cross a library function boundary); it returns the same value and costs a little extra gas per asset.
2. **The unchanged existing test suite.** The tests of the validated contracts were not edited except to link the new library when deploying `PoolLogic`: the changes to `test/PoolLogic.test.ts`, `test/PoolLogicAutoCompounding.test.ts`, `test/TokenLogic.test.ts` and `test/FrgmntUserActions.test.ts` are additions only (deploy `WithdrawalPlanLib` and pass it in `libraries`); no assertion was changed or removed. The whole suite passes (1293 tests).
3. **Bytecode and storage comparison.** Building the baseline and this branch and comparing compiled output shows: baseline storage slots 0–22 identical in slot, offset and type with new variables strictly appended; and, of the contract artifacts common to both builds, every one has identical runtime bytecode except `PoolLogic` (and four test mocks: `MockAaveV3Pool`, `MockERC20Custom`, `MockMorphoBlue`, `TestPoolManagerLogic`); `scripts/compare-with-baseline.js` reproduces this, the storage-layout check and the ABI check. Contracts that merely import `IPoolLogic` or `IPoolManagerLogic` can differ in the trailing compiler metadata hash only, which matters if exact-match block-explorer verification of a freshly redeployed `FundCalculationLibrary` or `PoolTxExecutor` is required.

An additional opt-in rehearsal (`test/UpgradeFromAudit.test.ts`) deploys the real `audit`-branch `PoolLogic` behind a transparent proxy, creates real staker state, upgrades to this branch, and checks that slots 0–22 are byte-identical, every getter is preserved, and a staker's pending reward survives the migration and harvests in full.

### 6.1 Findings before implementation

This design was reviewed before implementation planning, specifically because it introduces the hottest, most-automated signing key of any role in the protocol and a new delegatecall-based architecture needed just to fit within `PoolLogic`'s remaining bytecode budget, both are exactly the kind of change that deserves more scrutiny than a first pass gets. Points are listed most-severe first; every one is resolved in the sections above, not just noted here.

**Considered and confirmed not to need a fix** (worth recording so they aren't re-litigated later):

- A `delegatecall` into the library executes in the same call frame and storage context as the `nonReentrant`-guarded outer call, it introduces no new reentrancy boundary, the same way `PoolTxExecutor.exec()`'s existing delegatecall doesn't around `execTransaction()`.
- The EIP-712 domain separator (hand-rolled in `WithdrawalPlanLib`, equivalent to `EIP712Upgradeable`'s) already binds `chainId` and `verifyingContract`; no extra pool-identifying field is needed inside `WithdrawalPlan` to prevent cross-contract/cross-chain replay.
- An empty `allocations` array is rejected automatically by the lower value-conservation bound (a zero delta fails against any `netFusd > 0`), no special-case code needed.
- The fixed dust-level upper-bound tolerance is not economically farmable across many transactions; gas cost dominates the extractable amount by orders of magnitude. (A later internal review round noted the tolerance is absolute and the breaker meters `netFusd`, which matters on a cheap L2; the `MIN_PLAN_NET_FUSD` floor bounds it, see [Findings during implementation and review](#62-findings-during-implementation-and-review) and [Security analysis](#312-security-analysis).)
- The circuit breaker being pool-wide rather than per-user is an intentional trade-off: a per-user cap wouldn't address the actual threat (one compromised key acting across many different users' own, individually-legitimate withdrawals).

## 7. Open questions

0. **Items still open after review.** (a) The rehearsal against real mainnet state (real staker balances, queued requests, the escrow step) has not been run; the audit-implementation rehearsal covers layout and one staker's reward migration only. (b) The upgrade and deploy scripts have not been run against a live network. (c) `attestedWithdrawDecayWindow` has no setter ceiling, but the library treats any value above 30 days as 30 days (an absurd value can no longer overflow the accumulator and disable the feature); `attesterRotationDelay` (`factoryOwner`-only) still has no ceiling, and an absurd value only makes `proposeWithdrawalAttester` overflow-revert until the `factoryOwner` sets a sane one. (e) The circuit breaker bounds a compromised attester key, not a compromised manager: the manager can raise the volume cap or shorten the decay window at once, so the independent control against a colluding manager is the `factoryOwner`'s latched stop (see Security Considerations). (d) Position selection for debt-bearing positions (Morpho markets with an open borrow, an Aave V3 account with any debt) is not offered; it would need a partial flash-loan unwind.

1. **Partial fills.** Should a single signed plan be spendable across multiple transactions (e.g., attester signs "up to X", user draws down incrementally)? v1 assumes single-use, exact-match `fusdAmount` for simplicity; revisit if attester-service latency/cost makes per-request signing too expensive at scale.
2. **Circuit-breaker window sizing.** `attestedWithdrawDecayWindow` and `maxAttestedWithdrawVolumePerWindow` (above their respective floors) need real usage data to calibrate, too tight and the feature becomes unusable during genuine high-demand periods; too loose and it stops meaningfully bounding a compromise. Propose launching conservative and adjusting via telemetry rather than guessing a permanent value upfront.
3. **Multiple attesters / threshold signing.** Out of scope for v1 (single attester address), but the two-sided value bound plus the circuit breaker mean the security cost of a single-key model is already fairly contained; a multi-sig or threshold-signed attester would primarily improve availability and reduce single-server compromise risk further, not fix a fund-safety gap that would otherwise exist.
